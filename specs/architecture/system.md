# System map

Owner: Vong maintainers
Status: current
Last-Reviewed: 2026-08-19

## People and external systems

- Listener: owns an account, cloud-storage connections, library, playback history,
  favorites, playlists, and optional YouTube taste data.
- Google OAuth / Auth.js: signs listeners into Vong; storage and YouTube scopes are
  requested through separate OAuth flows.
- PostgreSQL (typically Neon): stores identity, encrypted connection credentials,
  library metadata, collections, scan state, listening history, and telemetry.
- Google Drive, Dropbox, and OneDrive: own media bytes and folder/file metadata.
- YouTube Music / InnerTube and YouTube Data API: provide search, metadata, home,
  radio continuation, optional taste import, and on-device audio resolution inputs.
- GitHub Releases: supplies latest-version metadata and native installer assets.

## Important flows

- Web sign-in -> Auth.js Google flow -> JWT session cookie -> user-scoped API access.
- Native sign-in -> system browser cookie session -> 120-second single-use handoff
  code -> native bearer JWT -> authenticated API and library-stream requests.
- TV/web device sign-in -> target-bound short-lived user code and hashed high-entropy
  target credential -> phone scan or manual entry -> authenticated explicit approval
  -> atomic one-use exchange -> native bearer JWT for TV or HttpOnly cookie for web.
- Connect storage -> provider OAuth -> encrypted token persistence -> select scan
  roots -> persisted scan job -> batched metadata range reads -> library rows.
- Play library track -> ownership lookup -> cached/refreshable provider credential ->
  redirect for Dropbox/OneDrive or bounded Range proxy for Google Drive -> active
  web/native audio engine.
- Play YouTube track -> server-provided metadata -> resolver running on the listener's
  device -> googlevideo URL -> native ranged byte reader, or official iframe on web.
- Start/refill radio -> authenticated YouTube up-next request -> persisted metadata ->
  client-side de-duplication and queue extension -> playback history and session-local
  blocked-track updates.
- Emit telemetry -> shared allowlist and sanitizer -> anonymous unauthenticated batch
  endpoint -> separate analytics table; delivery failure is swallowed by clients.

## Important boundaries

- Security/privacy: web cookies and native bearer tokens resolve through one Auth.js
  identity path; route/library queries add `userId` ownership predicates. Provider
  credentials are encrypted. Telemetry intentionally has no `userId` foreign key.
- Playback: only the engine for the current shell/source may be audible. YouTube
  audio URL resolution stays off server infrastructure. Native library requests keep
  the Vong bearer header; googlevideo requests must not receive that bearer header.
- Data ownership: Drizzle schema and migrations own storage shape; domain specs own
  current behavior; shared TypeScript/native bridge types and discovery shelf
  classification own executable cross-shell interface shapes; provider implementations
  own external API adaptation.
- Reliability/recovery: scans persist jobs/items and process bounded batches;
  unchanged remote revisions are skipped. OAuth refresh failure marks a connection
  for reauthorization. Telemetry failure is deliberately non-blocking.
- Generated code: `mobile/android/` is generated by Expo prebuild; native Android
  behavior is owned by config plugins and `mobile/modules/`, not generated output.
- Distribution: phone and TV are separate Android artifacts from one codebase. The
  phone APK targets arm64; the TV APK is universal ARM (`armeabi-v7a` + `arm64-v8a`)
  because TV firmware ABI cannot be inferred from the SoC instruction set.

## Evidence status and remaining verification gaps

- Code/schema-confirmed: component boundaries, API/auth flow, data ownership,
  provider stream modes, native bridges, scan batching, and telemetry separation.
- Test-confirmed: shared queue/radio/analytics/update behavior and core web flows for
  login, browsing, search, playlists, favorites, playback, seeking, and next-track.
- Code-confirmed: Windows hosts the shared web UI, while Android owns a separate Expo
  Router UI and consumes the shared queue/resolver contracts.
- Code/measurement-confirmed: every native googlevideo request needs a Range header;
  the current Rust and Android readers inject open-ended `bytes=N-` ranges.
- Later change evidence: the Android TV emulator exercised Leanback discovery,
  pairing API behavior, D-pad navigation, native Media3 playback, and MediaSession
  pause/resume. Physical Sony firmware and production deployment remain separate
  operational checks.
